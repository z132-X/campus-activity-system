# 校园活动管理系统 V1.0 — 需求分析

## 2.1 业务问题与用户目标

### 当前业务问题

业务背景给出的是一个很概括的方向：为校园活动的组织和学生参与提供信息化支持。
经过分析，当前真正需要解决的是**活动信息无法有效触达，且报名过程依赖人工统计**这一组问题，具体表现为：

1. **活动信息分散**：活动信息主要通过海报、群通知等方式传播，学生难以及时、完整地获取，容易遗漏。
2. **报名依赖人工统计**：普遍使用群接龙或共享表格收集报名，容易出现重复报名、超额报名、核对困难。
3. **组织者缺少管理手段**：教师无法实时掌握报名人数和名单，活动变更（时间调整、取消）难以及时告知已报名学生。

因此 V1.0 的核心不是"做一个功能齐全的门户网站"，而是**让"发布活动 → 学生报名 → 教师管理"这条主链路在线上闭环成立**，并让报名数据可信、可查。

### 用户与核心目标

| 用户/角色 | 希望通过系统完成什么 | 核心目标 |
|---|---|---|
| 学生 | 查看可参与的活动并完成报名，必要时取消 | 及时获取活动信息，报名状态明确、可查 |
| 活动组织教师 | 发布活动、设定人数与时间、查看报名名单、必要时取消活动 | 掌握报名情况，报名数据准确、可追溯 |

两类用户对系统的诉求是互补的：学生侧关注"能不能报上、报上没有"，教师侧关注"有多少人报、是谁报的"。
V1.0 的所有需求都围绕这两点展开。

## 2.2 V1.0 需求

| 编号 | 用户/角色 | 需求描述 | 优先级 | 验收依据 |
|---|---|---|---|---|
| REQ-01 | 全体用户 | 用户注册账号并选择身份（学生 / 教师），使用账号和密码登录；登录后按身份进入对应功能视图 | 高 | 注册成功写入用户表且密码以哈希形式存储；密码错误无法登录；未登录访问功能页面跳转至登录页 |
| REQ-02 | 学生 | 浏览已发布的活动列表，查看活动详情（标题、描述、地点、起止时间、容量、剩余名额、报名截止时间） | 高 | 列表仅展示状态为"已发布"的活动；已取消活动不可见；剩余名额 = 容量 − 有效报名数，计算正确 |
| REQ-03 | 学生 | 对处于报名期内且未满员的活动提交报名 | 高 | 报名成功写入报名表；满员、已过截止时间、重复报名、活动已取消四种情况均被拒绝并给出明确提示 |
| REQ-04 | 学生 | 查看自己已报名的活动列表，并在报名截止前取消报名 | 中 | 我的报名列表与数据库记录一致；取消后名额释放；已过报名截止时间的活动不允许取消 |
| REQ-05 | 教师 | 发布活动，填写标题、描述、地点、开始与结束时间、容量、报名截止时间 | 高 | 发布成功写入活动表且发布者为当前教师；必填项缺失或时间逻辑错误（开始 ≥ 结束、截止晚于开始）时被拒绝 |
| REQ-06 | 教师 | 管理自己发布的活动：查看报名名单、关闭报名、取消活动 | 高 | 教师仅能看到并操作自己发布的活动；活动取消后学生端不可见且状态标记为已取消；名单人数与实际有效报名一致 |

需求编号 REQ-01 ~ REQ-06 在后续的工程意图、软件设计、Git 提交记录与验证用例中被统一引用，用于建立可追踪关系。

## 2.3 需求取舍与范围控制

V1.0 的目标是让主链路闭环成立，而不是功能数量最多。以下候选需求经过分析后**暂不纳入本轮**，并记录理由：

| 被舍弃的候选需求 | 暂不实现的原因 |
|---|---|
| 管理员角色与活动审核流程 | V1.0 假定教师可自主发布活动，引入审核流会新增一整条审批链路和对应的状态管理，却不堵塞"发布—报名—管理"主链路。若后续版本需要内容把关，再引入审核状态。 |
| 消息通知（站内信、邮件、短信提醒） | 通知依赖外部服务与额外的用户触达配置，且学生对活动的获知在 V1.0 可通过主动浏览列表满足。活动取消的告知通过活动状态在列表中体现。 |
| 活动签到与学分认定 | 签到涉及现场凭证（二维码、定位）与学时/学分规则，属于另一条独立业务，与"报名"是不同阶段的问题，不应在 V1.0 混入。 |
| 活动分类、标签、搜索与分页 | V1.0 数据规模很小（单校单学期活动量级在数十到数百），列表直接展示即可满足，过早引入检索与分页会增加复杂度而无实际收益。 |

**范围控制原则**：凡是不影响"发布—报名—管理"闭环成立的功能，一律推迟到后续版本；
凡是与报名数据准确性直接相关的规则（重复报名、容量、截止时间），一律在 V1.0 内做实。
