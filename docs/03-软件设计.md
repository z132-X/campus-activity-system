# 校园活动管理系统 V1.0 — 软件设计

## 4.1 总体设计

系统采用**服务端渲染的四层结构**，自上而下为：

```
表示层  templates/*.html        Jinja2 模板，只负责渲染与展示，不含业务判断
   ↓
路由层  app/routes/*.py         接收请求、校验参数、调用服务层、决定跳转与提示
   ↓
服务层  app/services/*.py       业务规则与校验（报名规则、权限归属、时间逻辑）
   ↓
数据层  app/db.py + schema.sql  SQLite 连接、表结构定义、SQL 执行
```

分层约定：

- **路由层不写业务规则**，只做"取参数 → 调服务 → 根据结果渲染或重定向"；
- **服务层不依赖 HTTP 对象**（不直接读 request / session），保证规则可独立测试；
- **SQL 只出现在数据层**，服务层通过函数访问数据。

模块划分与需求对应：

| 模块 | 文件 | 对应需求 |
|---|---|---|
| 认证 | `app/routes/auth.py`、`app/services/user_service.py` | REQ-01 |
| 活动 | `app/routes/activity.py`、`app/services/activity_service.py` | REQ-02、REQ-05、REQ-06 |
| 报名 | `app/routes/registration.py`、`app/services/registration_service.py` | REQ-03、REQ-04 |

## 4.2 核心业务流程

### 流程一：学生查看活动并报名（REQ-02、REQ-03）

```
学生登录
  → 浏览活动列表（仅展示 status = published 的活动，含剩余名额）
  → 打开活动详情
  → 点击「报名」
  → 服务端依次校验：
       ① 身份是否为学生        否 → 拒绝：教师账号不可报名
       ② 活动是否仍为已发布    否 → 拒绝：活动已取消或报名已关闭
       ③ 当前时间 ≤ 报名截止    否 → 拒绝：报名已截止
       ④ 剩余名额 > 0          否 → 拒绝：名额已满
       ⑤ 是否已有效报名        是 → 拒绝：不可重复报名
  → 全部通过：写入/更新报名记录（status = active）
  → 返回活动详情页并提示报名成功，剩余名额同步减少
```

### 流程二：教师发布并管理活动（REQ-05、REQ-06）

```
教师登录
  → 填写活动表单（标题、描述、地点、起止时间、容量、报名截止）
  → 服务端校验：
       ① 身份是否为教师        否 → 拒绝
       ② 必填项是否完整        否 → 拒绝并指出缺失项
       ③ 开始时间 < 结束时间   否 → 拒绝
       ④ 报名截止 ≤ 开始时间   否 → 拒绝
       ⑤ 容量为正整数          否 → 拒绝
  → 全部通过：写入活动（status = published，publisher_id = 当前教师）
  → 教师可在「我的活动」中：
       · 查看报名名单（有效报名学生及其报名时间）
       · 关闭报名（status = closed，学生不可再报）
       · 取消活动（status = cancelled，学生端不可见，相关报名置为失效）
```

## 4.3 数据设计

共三张表，结构定义见 `schema.sql`。

### users（用户）

| 字段 | 类型 | 说明 | 约束 |
|---|---|---|---|
| id | INTEGER | 用户主键 | PRIMARY KEY AUTOINCREMENT |
| username | TEXT | 登录账号 | NOT NULL, UNIQUE |
| password_hash | TEXT | 密码哈希值（不明文） | NOT NULL |
| role | TEXT | 身份：student / teacher | NOT NULL, CHECK(role IN ('student','teacher')) |
| display_name | TEXT | 显示姓名 | NOT NULL |
| created_at | TEXT | 注册时间 | NOT NULL |

### activities（活动）

| 字段 | 类型 | 说明 | 约束 |
|---|---|---|---|
| id | INTEGER | 活动主键 | PRIMARY KEY AUTOINCREMENT |
| title | TEXT | 活动标题 | NOT NULL |
| description | TEXT | 活动描述 | 可为空 |
| location | TEXT | 活动地点 | NOT NULL |
| start_time | TEXT | 开始时间 | NOT NULL |
| end_time | TEXT | 结束时间 | NOT NULL |
| capacity | INTEGER | 容量上限 | NOT NULL, CHECK(capacity > 0) |
| deadline | TEXT | 报名截止时间 | NOT NULL |
| status | TEXT | published / closed / cancelled | NOT NULL, CHECK(...) |
| publisher_id | INTEGER | 发布教师 | NOT NULL, REFERENCES users(id) |
| created_at | TEXT | 创建时间 | NOT NULL |

### registrations（报名）

| 字段 | 类型 | 说明 | 约束 |
|---|---|---|---|
| id | INTEGER | 报名主键 | PRIMARY KEY AUTOINCREMENT |
| user_id | INTEGER | 报名学生 | NOT NULL, REFERENCES users(id) |
| activity_id | INTEGER | 报名活动 | NOT NULL, REFERENCES activities(id) |
| status | TEXT | active / cancelled | NOT NULL, CHECK(...) |
| created_at | TEXT | 报名时间 | NOT NULL |
| — | — | **同一用户对同一活动仅一条记录** | **UNIQUE(user_id, activity_id)** |

### 数据关系

```
users ──1:N──> activities        （一名教师可发布多个活动，publisher_id）
users ──1:N──> registrations     （一名学生可有多条报名，user_id）
activities ──1:N──> registrations（一个活动可有多条报名，activity_id）
```

关键派生数据（不在表中冗余存储，查询时计算）：

- 有效报名数 = `COUNT(registrations WHERE activity_id = ? AND status = 'active')`
- 剩余名额 = `capacity − 有效报名数`

## 4.4 关键设计约束或决策

### 决策 1：角色用 `users.role` 单字段 + CHECK 约束，不建独立的角色表与权限表

**理由**：V1.0 只有学生、教师两级身份，且不存在角色组合或细粒度权限需求。独立权限表会引入额外的关联查询与维护成本，收益为负。
用 `CHECK` 约束在数据库层兜底，可防止非法角色值被写入；权限判断集中在服务层的 `require_role()`，服务端强制，不依赖页面隐藏。
若后续出现第三类角色或需要按功能授权，再将角色与权限拆表——届时可平滑迁移，不影响现有三张主表。

### 决策 2：重复报名由数据库 `UNIQUE(user_id, activity_id)` 保证，而非应用层查询判断

**理由**：应用层"先查询再写入"存在竞态窗口——两个并发请求可能同时通过检查、随后双双写入，导致重复报名。
数据库唯一约束是最终防线，无论并发如何都不会产生重复记录。
应用层仍保留查询，但**作用仅限于给出友好提示**（"你已报名过该活动"），不承担正确性责任。

配套实现策略：由于取消了不物理删除，报名写入采用"存在则更新、不存在则插入"：

- 无记录 → `INSERT`（status = active）
- 有记录且为 `cancelled` → `UPDATE` 为 active（支持取消后重新报名）
- 有记录且为 `active` → 拒绝（重复报名）

这样唯一约束始终成立，且不会因历史记录阻塞重新报名。

### 决策 3：取消报名使用状态标记（active / cancelled），不做物理删除

**理由**：物理删除会丢失"该学生曾报名后又取消"这一事实，导致后续无法追溯，也会让名额统计出现歧义（删除后名额凭空恢复，与"取消"语义混淆）。
采用状态标记后，名额统计口径统一为 `status = 'active'`，清晰且可复算。
代价是数据量随时间增长，但在单校 V1.0 规模下可忽略；若将来需要归档，可按学期清理 `cancelled` 记录。

### 决策 4：密码使用 Werkzeug 的 `generate_password_hash` / `check_password_hash`，不自研加密

**理由**：口令存储是典型的高风险点，自研或使用弱哈希（MD5/SHA1 裸哈希）是常见安全错误。
Werkzeug 默认使用 PBKDF2 加盐迭代哈希，是 Flask 生态自带能力，无需引入额外依赖，也满足工程意图中的安全约束 8。
系统中任何位置都不出现明文密码，登录失败提示统一为"用户名或密码错误"，不区分具体原因，避免账号枚举。
