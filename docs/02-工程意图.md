# 校园活动管理系统 V1.0 — 工程意图

> 本文件在编码前形成，来源于已确认的 REQ-01~REQ-06，用于指导后续设计、实现与验证。
> 开发过程中若发现原有理解有问题，应先回到本文件重新判断，而不是直接扩大实现范围。

## 建设目的

V1.0 的建设目的**不是**做一个功能齐全的校园活动门户，而是：

> 用最小代价让"发布活动 → 学生报名 → 教师管理"这条主链路在线上闭环成立，并使报名数据可信。

拆开看是三件事：

1. 教师能自助发布活动并设置人数与截止时间，不再依赖群通知与人工转述；
2. 学生的每一次报名都有明确结果——报上了、没报上、以及没报上的具体原因（满员 / 已截止 / 重复报名）；
3. 报名数据成为**单一事实来源**，替代群接龙与共享表格，教师看到的名单就是真实报名情况。

判断这个目的是否达成，不看页面数量，只看一件事：**报名数据能不能被信任**。

## 本轮范围

**本轮完成**：REQ-01 ~ REQ-06 共六项需求，覆盖注册登录、活动浏览、报名、我的报名、教师发布活动、教师管理活动与名单。

**明确不在本轮范围内**（理由见需求分析 2.3）：

- 管理员角色与活动审核流程
- 消息通知（站内信、邮件、短信）
- 活动签到与学分认定
- 活动分类、标签、搜索、分页
- 附件上传、富文本编辑、头像与资料完善、密码找回

范围判据：凡不影响主链路闭环的，一律推迟；凡与报名数据准确性直接相关的，一律做实。

## 重要约束

### 业务约束

1. **角色边界**：身份在注册时确定（学生 / 教师），V1.0 不提供角色切换，也不提供权限提升入口。
   学生不能发布活动，教师不能报名活动。该限制必须在服务端强制，不能只靠页面隐藏按钮。
2. **报名规则**：一次报名必须同时满足——活动处于已发布状态、未过报名截止时间、剩余名额大于 0、该学生无有效报名记录。
   任一不满足都应被拒绝并给出具体原因。
3. **数据归属**：教师只能查看和操作自己发布的活动，不得越权访问他人活动及其报名名单。
4. **取消规则**：报名截止时间之后不允许取消，避免临近活动时的名额反复抖动；活动已取消时，其报名记录同步置为失效。

### 数据约束

5. **重复报名的唯一性由数据库唯一约束保证**（`UNIQUE(user_id, activity_id)`），不依赖应用层 if 判断，避免并发下出现重复写入。
6. **活动状态使用明确的状态机**：已发布 / 报名已关闭 / 已取消，不使用布尔开关拼凑。
7. **取消报名采用状态标记而非物理删除**，保留记录以便追溯，同时保证名额可正确释放。

### 安全约束

8. **密码必须哈希加盐存储**，任何情况下不保存明文，不在日志、页面或错误信息中回显。
9. **所有写操作必须校验登录身份与数据归属**，不能只验证"已登录"。
10. **仓库与代码中不得出现密钥、Token、真实个人隐私数据**，相关文件由 .gitignore 排除。

### 技术约束

11. **服务端渲染**，不引入前端构建工具链（不做 npm 打包、不做前后端分离），降低与业务无关的工程复杂度。
12. **数据库使用 SQLite**，结构定义以 `schema.sql` 为唯一依据，运行时数据文件不纳入版本库。
13. **保持分层**：路由层只做参数校验与跳转，业务规则集中在服务层，SQL 集中在数据层。路由中不写业务逻辑。

## 完成依据

同时满足以下全部条件，即认为 V1.0 达到预期目标：

1. REQ-01 ~ REQ-06 六项需求全部可实际操作，无占位实现、无空壳页面；
2. 每条需求对应的验证用例（TEST-01 ~ TEST-06）全部通过，且既覆盖正常业务过程，也覆盖关键异常情况；
3. 四类关键业务规则被实际验证为有效：重复报名被拒、满员被拒、已过截止被拒、越权访问被拒；
4. 报名数据与界面展示一致：教师端名单人数 = 有效报名数，且与活动剩余名额的推算相互吻合；
5. 需求、工程意图、设计、Git 提交、验证之间编号可对应，形成可追踪链路。
